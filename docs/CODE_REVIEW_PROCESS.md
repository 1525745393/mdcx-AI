# MDCx 代码审查流程指南

## 一、流程概述

本流程定义了 MDCx 项目的代码审查标准操作流程，确保所有代码变更都经过充分审查，保持代码质量。

### 1.1 流程目标
- 确保代码质量一致性
- 减少 bug 和技术债务
- 促进团队知识共享
- 加速开发效率

### 1.2 适用范围
- 所有开发者
- 所有代码变更（Bug 修复、功能开发、重构等）
- Pull Request 和 Merge Request

## 三、详细步骤

### 步骤 1：创建功能分支

```bash
# 1. 从最新主分支创建功能分支
git checkout main
git pull origin main
git checkout -b feature/your-feature-name

# 2. 分支命名规范
# 功能开发：feature/功能名称
# Bug 修复：bugfix/问题描述
# 重构：refactor/重构内容
# 文档：docs/文档内容
```

### 步骤 2：代码实现

遵循以下原则：
- **小步提交**：每次提交只做一件事
- **清晰的提交信息**：描述做了什么，为什么
- **及时保存**：避免丢失工作

### 步骤 3：本地检查

```bash
# 在提交前运行以下检查

# 1. 代码风格检查
ruff check .

# 2. 类型检查
mypy mdcx

# 3. 单元测试
pytest -v

# 4. 覆盖率检查
pytest --cov=mdcx --cov-report=html

# 5. 安全检查
bandit -r mdcx
safety check

# 6. 完整检查（推荐）
make check  # 如果项目有 Makefile
```

### 步骤 4：提交 Pull Request

#### PR 标题格式
```
<类型>: <简短描述>

类型：
- feat: 新功能
- fix: Bug 修复
- refactor: 重构
- docs: 文档更新
- style: 代码格式
- test: 测试更新
- chore: 杂项

示例：
feat: 添加 VSMETA 自定义模板功能
fix: 修复文件命名时的编码问题
refactor: 重构数据库连接管理
```

#### PR 描述模板
```markdown
## 变更概述
简要描述本次变更的内容。

## 解决的问题
- Issue #123: 描述问题

## 变更类型
- [ ] Bug 修复
- [ ] 新功能
- [ ] 重构
- [ ] 文档更新
- [ ] 其他

## 变更详情
详细描述变更的内容。

## 测试情况
- [ ] 单元测试通过
- [ ] 手动测试通过
- [ ] 覆盖率提升

## 截图/日志
（如有 UI 变更或错误修复）

## 检查清单
- [ ] 代码风格检查通过
- [ ] 单元测试通过
- [ ] 类型检查通过
- [ ] 文档已更新（如需要）
```

### 步骤 5：自动化检查

CI 系统会自动运行以下检查：

```yaml
# 检查项目
- 代码风格 (Ruff)
- 类型检查 (MyPy)
- 单元测试 (Pytest)
- 测试覆盖率
- 安全扫描 (Bandit)
- 依赖安全 (Safety)
```

**通过标准**：所有检查必须通过

### 步骤 6：代码审查

#### 审查者职责
1. **及时响应**：收到审查请求后 24 小时内响应
2. **全面审查**：按照审查清单逐项检查
3. **建设性反馈**：提出改进建议而非批评
4. **明确结论**：给出清晰的通过/修改/拒绝意见

#### 审查要点
按照 [CODE_REVIEW_STANDARDS.md](./CODE_REVIEW_STANDARDS.md) 执行

#### 反馈方式
- 使用 GitHub PR 评论功能
- 标记问题严重程度
- 提出具体的修改建议

### 步骤 7：修复和再次审查

```bash
# 1. 根据反馈修改代码
git checkout feature/your-feature-name
git pull origin main  # 确保最新
# 修改代码

# 2. 提交修改
git add .
git commit -m "fix: 响应审查反馈的修改"
git push origin feature/your-feature-name

# 3. 回复审查评论，说明修改内容
# 在 PR 中 @ 审查者
```

### 步骤 8：批准和合并

#### 合并条件
- ✅ 所有自动化检查通过
- ✅ 至少 1 位审查者批准（重要变更需 2+）
- ✅ 无未解决的重要问题
- ✅ 文档已更新（如需要）

#### 合并操作
```bash
# 1. 确保分支最新
git checkout feature/your-feature-name
git pull origin main

# 2. 合并到主分支
git checkout main
git pull origin main
git merge feature/your-feature-name

# 3. 推送
git push origin main

# 4. 删除功能分支（可选）
git branch -d feature/your-feature-name
git push origin --delete feature/your-feature-name
```

## 四、不同场景的审查流程

### 场景 1：紧急 Bug 修复

**目标**：快速修复，关键时期可以简化审查

```
流程：
1. 创建 hotfix 分支
2. 快速审查（可跳过部分检查）
3. 合并前必须审查
4. 优先合并到 main
5. 后续补充测试和文档
```

**要求**：
- 必须有人审查
- 可以接受较小范围的检查
- 必须在 24 小时内补充完整测试

### 场景 2：大功能开发

**目标**：充分讨论，分阶段审查

```
流程：
1. 创建 feature 分支
2. 先提交设计文档
3. 设计评审
4. 分阶段开发（每个阶段审查）
5. 最终集成审查
6. 完整测试
```

**要求**：
- 需要 2+ 审查者
- 必须有设计评审
- 单元测试覆盖率 > 80%
- 必须有使用文档

### 场景 3：代码重构

**目标**：确保功能不变，性能不降

```
流程：
1. 创建 refactor 分支
2. 制定重构计划
3. 重构前性能基准测试
4. 渐进式重构（每步审查）
5. 重构后性能对比
6. 完整测试
```

**要求**：
- 功能必须完全保持
- 性能不能退化
- 必须有测试保障
- 建议结对重构

## 五、审查时间要求

### 响应时间
| 优先级 | 首次响应 | 最终完成 |
|--------|---------|---------|
| 紧急 Hotfix | 2 小时内 | 24 小时内 |
| 高优先级 PR | 8 小时内 | 48 小时内 |
| 普通 PR | 24 小时内 | 72 小时内 |
| 低优先级 PR | 48 小时内 | 1 周内 |

### 超时处理
- **超时未响应**：提醒审查者
- **超时未审查**：升级给维护者
- **持续超时**：审查者轮换

## 七、常见问题处理

### Q1: 审查者和作者意见不一致怎么办？
**处理流程**：
1. 充分讨论，理解对方观点
2. 寻求折中方案
3. 如仍无法达成共识，升级给维护者
4. 维护者有最终决定权

### Q2: 紧急情况需要跳过审查怎么办？
**处理流程**：
1. 说明紧急原因
2. 获得维护者口头批准
3. 标记为 `[hotfix]`
4. 后续补充审查和测试
5. 总结经验教训

### Q3: 审查影响开发进度怎么办？
**解决方案**：
- 优化审查流程，提高效率
- 分解大 PR 为小 PR
- 提前沟通，预留审查时间
- 异步审查，提高响应速度
