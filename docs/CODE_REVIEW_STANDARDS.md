# MDCx 代码审查标准与流程规范

## 一、文档概述

### 1.1 目的
本文档旨在建立系统化的代码审查机制，统一代码质量标准，提升整体代码质量，确保项目的可维护性和稳定性。

### 1.2 适用范围
- 所有提交到主分支的代码变更
- Pull Request (PR) 审查
- 代码合并前的质量把控

### 1.3 目标
- 提高代码质量一致性
- 减少 bug 引入
- 促进知识共享
- 加速团队成长

## 二、代码审查标准

### 2.1 代码风格标准

#### 2.1.1 Python 代码规范
| 检查项 | 标准 | 优先级 |
|--------|------|--------|
| 缩进 | 使用 4 个空格 | P0 |
| 行长度 | 最大 120 字符 | P1 |
| 命名规范 | 函数使用 snake_case，类使用 PascalCase | P0 |
| 导入顺序 | 标准库 → 第三方库 → 本地模块 | P1 |
| 文档字符串 | 所有公共函数和类必须有 docstring | P0 |
| 类型注解 | 推荐使用类型注解 | P2 |

#### 2.1.2 代码组织规范
```
模块结构：
├── 单一职责原则
│   └── 每个模块/函数只做一件事
├── 高内聚低耦合
│   └── 相关功能放在一起，减少依赖
└── 清晰的层次结构
    └── 分层清晰，依赖方向一致
```

#### 2.1.3 注释规范
| 类型 | 要求 | 示例 |
|------|------|------|
| 文件头注释 | 包含版权、作者、日期、模块说明 | ```python# -*- coding: utf-8 -*-``` |
| 函数注释 | 描述功能、参数、返回值、异常 | Google Style 或 NumPy Style |
| 行内注释 | 解释"为什么"而非"是什么" | `# 使用缓存避免重复计算` |
| TODO 注释 | 标注待完成事项 | `# TODO: 优化性能` |

### 2.2 功能性标准

#### 2.2.1 正确性检查
- [ ] **逻辑正确性**
  - [ ] 算法的逻辑是否正确
  - [ ] 边界条件是否正确处理
  - [ ] 异常流程是否覆盖

- [ ] **数据处理**
  - [ ] 输入验证是否充分
  - [ ] 数据类型转换是否安全
  - [ ] 编码处理是否正确（UTF-8、Unicode）

- [ ] **资源管理**
  - [ ] 文件/网络连接是否正确关闭
  - [ ] 内存是否及时释放
  - [ ] 锁/信号量是否正确使用

#### 2.2.2 完整性检查
- [ ] **错误处理**
  - [ ] 是否捕获了所有可能的异常
  - [ ] 异常信息是否足够清晰
  - [ ] 是否有合适的降级策略

- [ ] **边界条件**
  - [ ] 空输入处理
  - [ ] 极大/极小值处理
  - [ ] 并发场景处理

### 2.3 性能标准

#### 2.3.1 效率要求
- [ ] **算法复杂度**
  - [ ] 时间复杂度是否合理
  - [ ] 空间复杂度是否合理
  - [ ] 是否有更优算法

- [ ] **资源使用**
  - [ ] 数据库查询是否优化（避免 N+1）
  - [ ] 缓存策略是否合理
  - [ ] 大文件处理是否流式化

#### 2.3.2 性能测试
```python
# 性能基准测试示例
import time
import pytest

def test_performance_large_file_processing():
    """处理 100MB 文件应在 5 秒内完成"""
    start = time.time()
    process_large_file("test_100mb.bin")
    duration = time.time() - start
    assert duration < 5.0, f"处理时间 {duration}s 超过 5s 限制"
```

### 2.4 安全标准

#### 2.4.1 安全检查清单
- [ ] **输入安全**
  - [ ] 用户输入是否经过验证
  - [ ] SQL 注入风险评估
  - [ ] 命令注入风险评估

- [ ] **敏感信息**
  - [ ] 禁止硬编码密码/密钥
  - [ ] API 密钥存储在环境变量
  - [ ] 日志脱敏处理

- [ ] **权限控制**
  - [ ] 文件操作权限检查
  - [ ] 网络访问权限控制
  - [ ] 配置文件的访问权限

### 2.5 可维护性标准

#### 2.5.1 代码可读性
- [ ] **命名清晰**
  - [ ] 变量名有意义（避免 a, b, c）
  - [ ] 函数名清晰表达功能
  - [ ] 常量定义有描述性名称

- [ ] **结构合理**
  - [ ] 函数长度不超过 100 行
  - [ ] 类的方法不超过 20 个
  - [ ] 模块不超过 500 行

#### 2.5.2 可测试性
- [ ] **测试覆盖**
  - [ ] 核心逻辑有单元测试
  - [ ] 边界条件有测试
  - [ ] 异常流程有测试

- [ ] **测试质量**
  - [ ] 测试之间无依赖
  - [ ] 测试结果稳定（无 flaky test）
  - [ ] 测试可独立运行

#### 2.5.3 可扩展性
- [ ] **设计模式**
  - [ ] 合理使用设计模式
  - [ ] 避免过度设计
  - [ ] 保持代码简单

- [ ] **配置化**
  - [ ] 硬编码值应提取为配置
  - [ ] 魔法数字应有命名常量

## 三、代码审查流程

### 3.1 审查角色定义

```
┌─────────────────────────────────────────────────────────┐
│                    审查角色                               │
├─────────────────────────────────────────────────────────┤
│  作者 (Author)                                           │
│  ├── 提交代码变更                                        │
│  ├── 响应审查反馈                                        │
│  └── 负责修复问题                                        │
├─────────────────────────────────────────────────────────┤
│  审查者 (Reviewer)                                       │
│  ├── 进行代码审查                                         │
│  ├── 提供建设性反馈                                       │
│  └── 批准或拒绝合并                                       │
├─────────────────────────────────────────────────────────┤
│  维护者 (Maintainer)                                     │
│  ├── 最终审批重要变更                                      │
│  ├── 处理审查争议                                         │
│  └── 维护代码质量标准                                      │
└─────────────────────────────────────────────────────────┘
```

### 3.2 审查流程图

```
作者提交代码
    │
    ▼
自动化检查
├── ✅ Lint 检查（代码风格）
├── ✅ 类型检查（mypy）
├── ✅ 单元测试
├── ✅ 安全扫描
└── ✅ 覆盖率检查

    │ 全部通过
    ▼
审查者审查
├── 功能性审查
├── 性能审查
├── 安全审查
└── 可维护性审查

    │ 通过
    ▼
合并到主分支
    │
    ▼
发布新版本
```

### 3.3 详细审查流程

#### 3.3.1 第一阶段：作者自检
```markdown
## 作者提交前检查清单

### 基础检查
- [ ] 代码风格检查通过
- [ ] 单元测试通过
- [ ] 类型检查通过
- [ ] 没有任何 TODO/FIXME 未完成

### 功能检查
- [ ] 新功能经过手动测试
- [ ] 边界条件已考虑
- [ ] 错误处理已添加

### 文档检查
- [ ] 函数/类已添加文档
- [ ] 复杂逻辑有注释说明
- [ ] CHANGELOG 已更新（如果需要）

### 提交信息检查
- [ ] 提交信息清晰描述变更
- [ ] 遵循提交信息规范
- [ ] 关联的 Issue 已关闭
```

#### 3.3.2 第二阶段：自动化检查
```yaml
# .github/workflows/code-review.yml
name: Code Quality Checks

on:
  pull_request:
    branches: [main, develop]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.13'
      - name: Install dependencies
        run: pip install ruff mypy pytest
      - name: Run Ruff (Linter)
        run: ruff check .
      - name: Run MyPy (Type Checker)
        run: mypy mdcx
      - name: Run Tests
        run: pytest --cov=mdcx

  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Security Scan
        run: |
          pip install bandit safety
          bandit -r mdcx
          safety check
```

#### 3.3.3 第三阶段：人工审查

##### 审查优先级

| 变更类型 | 审查深度 | 审查人数 | 要求 |
|---------|---------|---------|------|
| Bug 修复 | 中等 | 1 人 | 通过 |
| 小功能 | 基础 | 1 人 | 通过 |
| 大功能 | 深入 | 2+ 人 | 所有通过 |
| 安全变更 | 深入 | 2+ 人 | 所有通过 + 维护者审批 |
| 重构 | 深入 | 2 人 | 通过 + 测试覆盖 |

##### 审查关注点

```
功能性审查 (40%)
├── 逻辑正确性
├── 边界条件处理
├── 错误处理完整性
└── 向后兼容性

代码质量审查 (30%)
├── 代码风格一致性
├── 命名清晰性
├── 复杂度合理性
└── 注释完整性

性能审查 (15%)
├── 算法复杂度
├── 资源使用效率
└── 缓存策略

安全审查 (15%)
├── 输入验证
├── 敏感信息处理
└── 权限控制
```

### 3.4 审查反馈规范

#### 3.4.1 反馈分类

| 标签 | 含义 | 处理要求 |
|------|------|---------|
| `blocker` | 阻塞性问题，必须修复 | 修复前不能合并 |
| `major` | 重要问题，建议修复 | 修复后合并 |
| `minor` | 小问题，可选修复 | 可直接合并 |
| `nitpick` | 格式/风格小问题 | 不影响合并 |
| `question` | 疑问，需要澄清 | 需要作者回复 |

#### 3.4.2 反馈模板

```markdown
## 代码审查反馈

### [blocker] 问题标题
**位置**: `src/module.py:42`
**问题描述**: 
这里存在空指针风险，如果 `data` 为 None 会导致异常。

**建议修复**:
```python
if data is None:
    return default_value
# 原有逻辑
```

---

### [major] 建议优化
**位置**: `src/processor.py:100-150`
**问题描述**: 
这个函数的复杂度为 O(n²)，当数据量大时性能会下降。

**建议优化**:
考虑使用哈希表将查找复杂度降低到 O(1)。

---

### [nitpick] 代码风格
**位置**: `src/utils.py:20`
**问题描述**: 
变量名 `a` 建议改为更描述性的名称。

---

### [question] 需要澄清
**位置**: `src/core.py:80`
**问题描述**: 
这里的逻辑不太理解，能解释一下为什么要这样处理吗？
```

## 四、不同变更类型的审查要求

### 4.1 Bug 修复审查

```
审查重点：
├── 复现步骤是否清晰
├── 根本原因分析是否正确
├── 修复方案是否完整
├── 是否引入新问题
└── 测试是否覆盖

审查问题清单：
- [ ] Bug 是否可复现？
- [ ] 修复是否治标又治本？
- [ ] 是否有相应的测试用例？
- [ ] 是否更新了相关文档？
```

### 4.2 新功能审查

```
审查重点：
├── 功能需求是否清晰
├── 设计是否合理
├── 是否影响现有功能
├── 是否有充分测试
└── 文档是否完整

审查问题清单：
- [ ] 功能是否完整实现？
- [ ] 边界条件是否处理？
- [ ] 错误处理是否完善？
- [ ] 性能是否可接受？
- [ ] API 设计是否一致？
- [ ] 是否有使用示例？
```

### 4.3 重构审查

```
审查重点：
├── 重构目标是否明确
├── 是否保持功能不变
├── 变更范围是否合理
├── 是否有测试保障
└── 是否有回滚方案

审查问题清单：
- [ ] 重构前后行为一致？
- [ ] 测试是否全部通过？
- [ ] 性能是否有退化？
- [ ] 是否引入技术债务？
- [ ] 是否有渐进式重构？
```

## 五、审查质量度量

### 5.1 审查效率指标

```python
# metrics.py
from dataclasses import dataclass
from datetime import datetime

@dataclass
class ReviewMetrics:
    """审查效率指标"""
    pr_id: str
    author: str
    reviewer: str
    created_at: datetime
    first_review_at: datetime  # 首次审查时间
    approved_at: datetime       # 审批通过时间
    changes_count: int          # 代码变更行数
    review_comments_count: int # 审查评论数
    blockers_count: int         # blocker 问题数

    @property
    def review_time_hours(self) -> float:
        """从创建到首次审查的时间（小时）"""
        delta = self.first_review_at - self.created_at
        return delta.total_seconds() / 3600

    @property
    def approval_time_hours(self) -> float:
        """从创建到审批通过的时间（小时）"""
        delta = self.approved_at - self.created_at
        return delta.total_seconds() / 3600

    @property
    def review_per_line(self) -> float:
        """每百行代码的审查评论数"""
        if self.changes_count == 0:
            return 0
        return self.review_comments_count / (self.changes_count / 100)
```

### 5.2 审查质量指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 首次审查时间 | < 24h | PR 创建到首次审查的时间 |
| 审查周期 | < 48h | PR 创建到合并的时间 |
| Blocker 率 | < 20% | 包含 blocker 的 PR 比例 |
| 返工率 | < 30% | 需要大改的 PR 比例 |
| 覆盖率 | > 80% | 有测试的代码行数占比 |
